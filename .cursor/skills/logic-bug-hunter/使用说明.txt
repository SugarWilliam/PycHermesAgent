
# Logic Bug Hunter 详细介绍

**Logic Bug Hunter** 是一个面向 C/C++ 应用的**逻辑 bug 深度分析** skill，重点处理逻辑错误和需求与实现不一致，适用于必现和偶现 bug。

---

## 一、定位与适用场景

| 适用场景 | 说明 |
|---------|------|
| 逻辑错误 | 条件写反、运算符用错、分支遗漏等 |
| 需求与实现不符 | 代码按实现是对的，但实现本身不符合设计 |
| 必现 bug | 固定输入/步骤可稳定复现 |
| 偶现 bug | 难以稳定复现，依赖时序、状态或环境 |
| 跨模块问题 | 单模块看起来正常，组合后出错 |

**触发词**：逻辑错误、逻辑 bug、需求不对、实现不对、行为不符合预期、偶现 bug、必现 bug、logic bug、wrong behavior、intermittent、requirement mismatch、root cause

---

## 二、输入要求

| 输入项 | 是否必需 | 作用 |
|--------|----------|------|
| Bug 描述 | ✅ 必需 | 实际发生的错误现象 |
| 预期结果 | ✅ 必需 | 按需求/设计应有的正确行为 |
| 运行时日志/打印 | 建议 | printf、syslog 等，用于还原现场 |
| 相关代码 | 建议 | 怀疑涉及的文件/函数 |
| 复现步骤 | 可选 | 如何触发（是否依赖顺序、时序等） |
| 需求/设计文档 | 可选 | 功能预期，帮助理解“意图” |
| 环境信息 | 可选 | OS、架构、构建配置、运行条件 |

**核心思路**：Bug 在“实际行为”和“预期行为”之间的差距里，这两个输入缺一不可。

---

## 三、七阶段分析流程

```
Phase 1: 差距刻画 → Phase 2: 日志分析 → Phase 3: 假设形成 → Phase 4: 上下文扩展与调用链追踪
    → Phase 5: 逻辑模拟与分歧检测 → Phase 6: 偶现 Bug 分析（如适用）→ Phase 7: 根因确认与修复
```

### Phase 1：差距刻画

- 明确行为差距：错在什么（值、动作、时序、目标）？错到什么程度？何时出现？
- 对 bug 分类：确定性逻辑错误、状态相关、偶现、需求不符、边界/跨模块、功能 A 改动导致 B 出问题等
- 提取约束：能稳定触发的场景、能正常工作的场景、是否曾经正常、是否伴随其他功能改动

### Phase 2：日志与打印分析

- **时间线重建**：按时间排序，找到“最后一次正确”和“第一次错误”的位置
- **变量值追踪**：从打印中还原变量变化，找出**首次偏离预期**的位置
- **控制流推断**：例如函数入口有日志但出口没有 → 可能崩溃或挂起；分支 A 被打印但预期是 B → 条件判断错误
- **差异分析**：有成功和失败两套日志时，对比找出第一个分歧点

### Phase 3：假设形成

生成 3–5 个按优先级排序的假设，例如：

1. 需求与实现不一致
2. 条件/分支错误（谓词、运算符、逻辑反了）
3. 状态污染/残留
4. 数据流错误
5. 时序/顺序依赖

每个假设需说明：怀疑的根因、要验证的代码区域、验证方法、如何解释所有现象。
**原则**：能解释全部现象的假设优先于只解释部分现象的。

### Phase 4：上下文扩展与调用链追踪

**原则**：不孤立分析代码，每个函数都在完整上下文中执行。

- **向上追踪**：从可疑函数到所有调用者，直到入口（main、事件处理、定时器、线程入口、IPC 等）
- **向下追踪**：从可疑函数到被调函数，直到系统调用、IPC、存储写入等“终点”
- **横向追踪**：跨模块数据流，关注共享状态（全局变量、共享内存、消息队列等）的读写与协议
- **功能 A→B 影响**：若 B 在 A 改动后出问题，分析 A 的 diff 与共享点，检查 B 的路径是否被破坏

### Phase 5：逻辑模拟与分歧检测

在完整上下文和调用链基础上，用复现场景**逐步模拟执行**：

- 从入口开始，按实际输入一步步走
- 在每个分支、赋值、函数调用处记录实际行为
- 与预期对比，找到**第一次偏离预期的那一行**，即为根因所在

### Phase 6：偶现 Bug 分析

偶现 bug 被视为“有隐藏前置条件的确定性 bug”，目标是找出该前置条件：

- **可变因素**：时序、系统状态、输入数据、资源压力等
- **竞态分析**：共享状态、并发访问、竞态窗口、导致出错的调度顺序
- **残留状态**：`static` 变量、缓存、状态机未回到空闲等
- **环境敏感**：对 sleep、select 超时、系统负载、特定数据模式等的依赖

### Phase 7：根因确认与修复

- 给出根因说明：位置、问题代码、机制、如何导致所有现象、触发条件
- 提出最小修复方案，并说明理由、副作用和风险
- 给出验证计划：回归测试、边界用例、偶现 bug 的压力测试

## 四、逻辑 Bug 模式速查

| 模式 | 典型现象 | 排查要点 |
|------|----------|----------|
| 条件反了 | 行为与预期相反 | 比较分支谓词与设计意图 |
| 运算符错误（`<` vs `<=`，`&&` vs `\|\|`） | 边界失败或恒真/恒假 | 逐项对照需求检查 |
| switch/if-else 漏分支 | 合法输入无处理 | 枚举所有合法输入，检查是否都有分支 |
| 用错变量 | 计算出错 | 核对变量名与意图 |
| 缓存未更新 | 使用旧数据 | 追踪每次写入后的缓存失效 |
| 重入时未重置状态 | 第一次正常，重试失败 | 检查错误/退出路径的清理 |
| 差一错误 | 首/尾元素错误、溢出 | 检查 `<` vs `<=`、起始下标、长度 |
| 跨模块语义不一致 | A 和 B 对同一数据理解不同 | 比较结构体、枚举、协议定义 |

## 五、调试打印建议

当日志不足时，可引导用户增加以下位置的打印：

1. **分支点**：打印走的是哪条分支及原因
2. **可疑操作前后**：打印输入和输出
3. **跨模块边界**：A 发出和 B 接收时的数据
4. **状态转换**：旧状态 → 新状态 + 触发事件
5. **循环迭代**：计数器与关键变量

对较大代码区域，可采用**二分法**：在中间加打印，根据正确/错误缩小范围，逐步收敛到 5–10 行。

---

## 六、输出报告结构

Skill 会按以下结构输出分析报告：

1. **行为差距**：实际 vs 预期、差距类型、触发条件
2. **日志证据**：最后正确点、首次错误点、变量偏离、控制流证据
3. **调用链分析**：入口、向上/向下链、跨模块数据流、分歧点
4. **假设列表**：按优先级排序，并标注是否解释全部现象
5. **根因**：位置、问题代码、机制、触发条件
6. **修复建议**：代码改动、理由、副作用
7. **验证计划**：回归、边界、压力测试

## 八、使用方法

您可以直接复制以下提示词模板来调用 `logic-bug-hunter`：

### 基础模板 (无日志时直接提问)

请使用 logic-bug-hunter 技能帮我深度分析(deep mode)并定位以下bug：

**1. 实际现象 (Bug Description):**
[在这里描述发生了什么错误，例如：设备断网重连后，AI告警事件停止上报，但视频流正常播放]

**2. 预期行为 (Expected Result):**
[在这里描述正确的行为应该怎样，例如：断网重连后，网络层应该通知事件模块重新建立长连接，并在有人员出现时正常发出AI告警]

**3. 相关的代码范围 (Relevant Code):**
- 主要逻辑可能在：`[比如：product/netpublic/network_event.c]`，函数 `[比如：handle_reconnect_event()]` 附近。
- (如果有) 直接贴出怀疑的代码片段或告诉AI需要审查的文件路径。

**4. 补充信息 (可选 / Optional):**
- [触发条件：比如这问题是必现的，还是跑一晚上才偶尔出现？]
- [系统环境：比如特定平台、进程间通信交互点等]

如果仅靠代码分析无法 100% 确定根因，请按照技能要求生成精准的调试打印点（printf/LOG）与插入行号，我将去复现并提供新日志。

### 带日志追查的高级模板 (已有出错日志时附上)

**1. 实际现象:**
(必须)[描述程序运行出错的具体表现。例如：初始化云台 (PTZ) 模块时总是收到 -1 的错误码，导致启动失败。]

**2. 预期行为:**

(可选 / Optional):
- [触发条件：比如这问题是必现的，还是跑一晚上才偶尔出现？]

**5. 运行时出错日志 (Runtime Error Logs):**
