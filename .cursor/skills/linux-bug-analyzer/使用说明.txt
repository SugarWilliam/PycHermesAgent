linux-bug-analyzer 是一个面向 Linux 用户态 C/C++ 缺陷诊断的技能，定义在 SKILL.md。它的核心不是“猜一个可能原因”，而是做证据驱动的根因分析：把事实、推断、假设、缺失证据分开，先缩小问题窗口，再给出最小修复方案和验证计划。它特别强调 Linux 语义边界，也就是应用代码、libc、内核行为、运行环境和部署配置之间的关系。

**它能解决哪些 Linux 上的 bug**
1. 崩溃类问题：比如 SIGSEGV、SIGABRT、SIGBUS、野指针、越界、UAF、栈溢出、堆损坏、ABI 或结构体布局不一致导致的崩溃。
2. 卡死和无响应：包括死锁、自锁、线程互相等待、阻塞 I/O、丢唤醒、忙等、epoll 或定时器误用。
3. 内存增长和 OOM：区分真实泄漏、缓存无界增长、分配器碎片、mmap 未释放、线程/子进程/FD 间接持有资源。
4. 文件描述符和 socket 问题：FD 泄漏、socket 泄漏、accept 失败、close 之后复用、EMFILE、半包/粘包、部分读写处理错误。
5. 文件 I/O 和网络协议问题：比如 read/write 不完整、EINTR/EAGAIN 处理错误、阻塞/非阻塞假设错误、EOF/对端关闭语义理解错误。
6. 信号、fork、exec、子进程异常：信号处理器不安全、信号屏蔽问题、waitpid 处理缺失、多线程 fork 风险、CLOEXEC 漏设。
7. 并发时序类偶现 bug：竞态、内存可见性问题、共享状态更新顺序错误、锁顺序错误。
8. 跨模块/跨进程数据损坏：结构体 packing、对齐、大小端、32/64 位宽度差异、序列化协议不一致。
9. 运行环境相关问题：启动失败、路径错误、权限问题、cwd、umask、环境变量、service 启动和交互式 shell 行为差异。

**它的工作方式**
1. 先收集输入：至少要有现象描述和期望行为，最好再给复现步骤、日志、相关代码、回溯、core、strace、/proc 信息、编译和运行环境。
2. 先建证据矩阵：把当前内容整理成事实、推断、假设、缺失证据、下一步动作。
3. 按症状选证据源：崩溃优先看 core 和回溯，I/O 优先看 syscall 时间线，卡死优先看所有线程栈，泄漏优先看 smaps、pmap、资源台账。
4. 重建时间线：找最后一个正常事件和第一个异常事件，把日志、trace、回溯帧映射到具体函数和状态。
5. 做调用链和资源生命周期分析：不仅看可疑行，还要向上找调用者、向下找被调函数、横向找共享状态、确认 ownership 和释放路径是否闭合。
6. 输出结论：给出根因位置、失效机制、为什么其他假设被排除、最小修复方案、修复风险、验证方案。

**怎么使用**
你可以直接把问题按下面这种方式描述给我，我就可以按这个 skill 的方法来分析。

1. 最简用法
现象：程序偶现崩溃，日志最后一行是 xxx
期望：收到非法消息后应丢弃，不应崩溃
复现：高并发压测 10 分钟后出现
证据：bt full、相关日志、可疑模块代码

2. 崩溃类问题推荐补充
core 文件信息
gdb 的 bt full
崩溃线程和 fault address
崩溃点附近函数和数据结构定义

3. 卡死类问题推荐补充
thread apply all bt
CPU 占用情况
线程状态
锁对象、等待点、epoll 或条件变量相关代码

4. I/O 或 socket 问题推荐补充
strace -ff -tt -T -e trace=network,desc 输出
errno
socket 收发代码
协议帧格式和异常报文样例

5. 泄漏类问题推荐补充
pmap、smaps、/proc/pid/fd、lsof
对象创建与释放路径
是否存在缓存、线程、子进程、mmap 持续增长

如果你要实际使用，我建议你的提问格式尽量包含这几项：

使用linux-bug-analyzer skill分析一下bug：
1. 现象是什么。
2. 正确行为应该是什么。
3. 是否稳定复现。
4. 最后一条正常日志和第一条异常日志分别是什么。
5. 相关代码在哪些文件。
6. 有没有回溯、core、strace、/proc 证据。

这个 skill 最适合“定位根因”和“设计验证路径”，尤其适合复杂的 Linux 用户态 C/C++ 问题；它不适用于 Linux 内核 bug 本身，也不鼓励在证据不足时直接下结论。
