embedded-testcase-reviewer 是一个面向嵌入式代码的“测试用例驱动评审” skill。它的核心功能不是泛泛做 code review，而是把测试用例逐条映射到代码实现，最后对每条用例只给三种结论：`Implemented`、`Not Implemented`、`Uncertain`。每个结论都必须带代码证据，比如入口函数、状态变量、状态机分支、跨芯片消息、GPIO 或外设输出路径。它适合 Linux 或 FreeRTOS 项目，也考虑了 GPIO、I2C、UART、SPI、SDIO、USB、多芯片交互、不同 ARM 平台、不同机型、宏和能力集差异这些嵌入式常见复杂度。最重要的一条约束是：如果机型、宏配置、bootloader、MCU 固件或外部仓库信息不清楚，它必须先要求补充信息，不能靠猜。

它现在的默认交付方式也固定了：除了聊天里给结论，还会把完整结果写到仓库根目录的 testcase_review.md 中，格式由 output-template.md 约束；判定标准由 verdict-rules.md 约束；代码追踪方式由 embedded-trace-checklist.md 约束。

**怎么用**
1. 准备输入。
   最少需要一个 Markdown 或文本格式的测试用例文档，加上要评审的代码范围。最好再补充目标机型、board type、关键编译宏、能力集、以及功能到底归 AP、MCU、bootloader 还是别的仓库负责。

2. 用自然语言触发它。
   你可以直接说：
   “按照这个测试用例文档评审代码，逐条判断是否实现，给证据并输出到 testcase_review.md”
   或者：
   “根据测试用例查代码，输出 Implemented / Not Implemented / Uncertain”

3. skill 会先做范围确认。
   它会先确认产品型号、宏配置、功能归属边界。如果这些信息会影响 verdict，它会先追问，而不是直接下结论。

4. 它再逐条评审。
   每条 testcase 都会被拆成：
   前置条件
   触发动作
   期望结果
   隐含状态转换
   然后从入口事件一路追到最终可见行为，比如网络命令、任务回调、状态更新、SPI/I2C/UART 消息、GPIO 输出。

5. 最后产出结果。
   默认输出包括：
   逐条 testcase verdict
   每条的代码证据
   `Uncertain` 所缺的信息
   按严重度汇总的问题清单
   并写入 testcase_review.md

**适合的场景**
- “这份测试用例在代码里到底有没有实现？”
- “哪些 case 明显不满足？”
- “哪些 case 因为缺少机型、宏、MCU 固件信息只能判不确定？”
- “这个嵌入式功能跨 AP 和 MCU，能不能把链路查完整？”

**不适合的场景**
- 板级实测
- 自动生成测试脚本
- 没有测试用例、只想做泛泛代码审查
- 明知缺少关键仓库还要求它脑补结论
